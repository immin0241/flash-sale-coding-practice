# [백엔드 · DevOps 포지션] 실전 과제형 코딩 테스트

**과제명**: 한정 수량 선착순 구매 시스템 (Flash Sale / Limited Stock Ordering System)
**출제 의도**: 동시성 제어, DB 트랜잭션 이해, 부하 상황에서의 시스템 설계, 장애 대응 및 관측 가능성(Observability) 역량 검증
**제출 방식**: GitHub 리포지토리 링크
**평가 기준**: 별도 비공개 문서로 관리되며, 사전 공개하지 않습니다.

---

## 1. 시나리오

당신은 한정판 상품을 판매하는 이커머스 서비스의 백엔드를 맡았습니다. 특정 상품은 재고가 **N개**뿐이고, 판매 시작과 동시에 수천 명의 사용자가 동시에 구매를 시도합니다. 재고보다 많이 팔리는 순간(overselling) 회사는 환불·CS·신뢰도 손실을 감당해야 합니다. **단 1건의 초과 판매도 허용되지 않습니다.**

---

## 2. 기능 요구사항 (Functional Requirements)

| # | 요구사항 |
|---|---|
| F1 | 상품 목록 및 실시간 재고 수량 조회 API |
| F2 | 구매 요청 API (사용자 ID, 상품 ID, 수량을 받아 주문 생성) |
| F3 | 재고 소진 시 이후 모든 요청은 명확한 실패 응답(예: `409 Conflict` 또는 `410 Gone`)으로 처리 |
| F4 | 동일 사용자의 중복 구매 방지 (사용자당 1회로 제한) |
| F5 | 특정 사용자의 주문 내역 조회 API |
| F6 | 관리자용: 특정 상품의 현재 판매 현황(성공/실패 건수, 잔여 재고) 조회 API |

---

## 3. 비기능 요구사항 (핵심 평가 포인트)

- **정합성(Correctness)**: 동시 다발 요청 상황에서도 재고가 음수가 되거나 초과 판매가 발생해서는 안 됩니다. 예외 없이.
- **성능(Performance)**: 아래 "테스트 조건"에 명시된 동시 요청 수를 합리적인 응답 시간 내에 처리해야 합니다.
- **관측 가능성(Observability)**: 요청 수, 성공/실패율, 응답 시간 등 최소한의 메트릭을 노출해야 합니다. (Prometheus 포맷 권장)
- **장애 내성(Resilience)**: 시스템이 의존하는 구성요소(Redis, DB 커넥션 풀 등) 중 하나가 죽었을 때 어떻게 반응하는지가 **의도된 설계**여야 합니다. "안내 없이 그냥 죽는 것"은 감점 대상입니다. (명시적 에러 응답이든, fallback이든 상관없으나 반드시 설계 근거를 문서화할 것)

## 4. 기술 스택 조건

- **언어**: Go 권장. 다른 언어를 쓴다면 README에 이유를 명시할 것.
- **컨테이너화**: `docker-compose up` 한 번으로 전체 시스템(앱 + DB + 필요 시 캐시/락 서버)이 로컬에서 뜰 것.
- **DB**: 자유 선택 (PostgreSQL, MySQL 등). 선택 이유를 README에 서술.
- **동시성 제어 방식**: 자유 선택. 단, 최소 1가지 방식을 명확한 근거와 함께 선택하거나, 2가지 이상을 구현해 비교할 것. (예: DB 비관적 락 `SELECT ... FOR UPDATE`, Redis 분산락, 메시지 큐 기반 순차 처리 등)

---

## 5. 테스트 조건 (제출 후 이 조건으로 검증합니다)

1. **기본 시나리오**: 재고 **100개** 상품에 대해 **동시 사용자 1,000명 이상**이 각각 1건씩 구매를 시도.
2. 부하 테스트 도구(k6, Locust, Vegeta 등)로 **재현 가능한 스크립트**를 리포지토리에 포함해서 제출.
3. **핵심 판정 지표**:
   - 최종 판매 성공 건수가 정확히 100건과 일치하는가
   - 실패한 요청이 명확한 에러 코드로 반환되는가 (타임아웃/500 에러로 죽는 건 실패)
   - 응답 시간(p95/p99)이 부하 테스트 리포트에 기록되어 있는가
4. **카오스 테스트**: 부하가 몰리는 도중 캐시/락 서버(혹은 DB)를 임의로 강제 종료해보고, 시스템이 어떻게 반응했는지 관찰 결과를 기록해서 제출할 것. (직접 `docker stop` 등으로 재현)

- AI 코딩 어시스턴트 사용은 허용됩니다. 다만 핵심 설계 판단(왜 이 락 방식을 골랐는지, 왜 이 격리수준을 썼는지)과 트러블슈팅 과정은 본인이 주도해야 하며, 추후 확인 질문에 답할 수 있어야 합니다.
